# 站内信收件箱存储

站内信没有外部网关：「投递」这个动作本身就是把一条消息写进订阅者的收件箱，
等客户端来拉。这一层因此同时被三个使用方碰到——引擎写、API 读、多个实例共享
同一份文件——它的写路径决定了聚合场景能跑多快。

## 文件格式：一行一个版本

收件箱是一个追加流。同一条目（`id` 相同）每次改写都在文件末尾追加一行新版本，
旧版本留在原处不删；读侧按 `id` 去重、取最后一行。

```
{"id":"digest-post_liked-dg1-P1001","body":"1 人赞了你的帖子","updated_at":"…"}
{"id":"digest-post_liked-dg1-P1001","body":"2 人赞了你的帖子","updated_at":"…"}
{"id":"digest-post_liked-dg1-P1001","body":"3 人赞了你的帖子","updated_at":"…"}
```

三条记录，一条消息。聚合卡片在窗口内每命中一次互动就要改写一次，如果改写等于
「重写整份文件」，成本随收件箱增长，热门帖子会把消费者拖成一条队列。追加一行的
成本与文件大小无关，这是这个格式存在的唯一理由。

**读侧必须取最后一行。** 引擎的 `JSONLInboxStore.List`、API 的
`api/app/inbox.py::_engine_inbox_items`、`api/app/message_center.py::get/list`
都按这个约定实现；按先出现的行渲染会显示过期的计数。

字段与时间格式（RFC3339、UTC）在写入侧就固定下来，与 API 的收件箱条目一一对应，
两侧共用同一份文件。跨语言格式约定由 `engine/internal/pipeline/inbox_format_test.go`
锁住：把 API 写出的行当固定输入，断言引擎能读回。

## 写入成本

| 操作 | 落盘动作 | 复杂度 |
| --- | --- | --- |
| `Save`（新条目） | 一次 `O_APPEND` 写 | O(1) |
| `Update`（改写卡片） | 一次 `O_APPEND` 写 | O(1) |
| `List`（读某订阅者） | 全量扫描 + 按 `id` 去重 | O(文件大小) |
| 压缩（按比例触发） | 全量读 + 原子替换 | O(文件大小) |

`List` 是 O(文件大小) 的，它只服务于测试与排障；线上读取收件箱的是 API 侧，
那边有自己的缓存与版本号机制。

## 压缩

追加流会积累被覆盖的历史行，所以到一定比例后做一次压缩：

- **触发条件**：文件 ≥ 1 MiB，且被覆盖的行超过总行数的一半；
- **做法**：全量读 → 按 `id` 保留最新 → 同目录临时文件 → `rename` 替换；
- **并发保护**：读完先比对文件大小，与读到的字节数不一致说明期间有别的进程写入，
  放弃这一轮（下轮再判断）。替换是原子的，进程中途被杀不会留下半截文件。

阈值取「一半」是因为再低的收益不足以抵消重写成本：文件最多长到活跃数据的两倍
左右，随后回落到一倍。

## 多实例共享同一份文件

索引只记条目 ID 与已经读到的偏移，条目内容不常驻内存。刷新策略按代价从低到高：

1. 文件身份不变（`os.SameFile`）且只是变长 → 只读新增的尾部；
2. 文件被替换（压缩换了 inode）或变短 → 全量重扫；
3. 末尾没有换行的残片不解析，留给下一次读——那是别的进程正在写的半行。

第 1 条是多实例下的关键：如果每次看到文件变大就全量重扫，别的实例每追加一条都会
让本进程读 O(n)，合并起来是 O(n²)。

## 实测

同一台机器、同一份生产者脚本（点赞事件 → 聚合步骤 → 站内信），8 worker、
`XW_PREFETCH=32`、1000 张卡片、关闭执行明细回写，只换收件箱实现：

| 实现 | 吞吐 | 收件箱文件 |
| --- | --- | --- |
| 改写整文件（旧） | 156 条/秒 | 332 KB |
| 追加版本 + 压缩（当前） | 13,104 条/秒 | 压缩后约 1 MB（30 万条积压） |

正确性同时校验：30 万条互动落成 1000 张卡片、每张 300 次、合计 300,000，没有丢计数。
抓一份 CPU profile 看剩余成本，`Update` 累计占 48.6%，其中 `appendEntry` 44.2%，
平铺热点是 `syscall.rawsyscalln`（62.3%）——也就是 `open`/`write`/`close` 本身，
不再是文件读写与内存分配。压缩只占 2.2%。

## 已知边界

- **压缩与其它实例的追加之间有窗口**：压缩是「读全量 → rename」，如果别的实例
  恰好在读完之后、替换之前追加了一行，那一行会随替换丢失（表现为卡片计数少一次）。
  窗口是毫秒级，触发频率是「废弃行过半」，实际影响很小；彻底解决需要跨进程文件锁，
  当前没做。
- **每次追加都 `open`+`write`+`close`**：profile 显示这是剩下的大头。换成常驻句柄
  能省两次系统调用，但要处理「压缩换 inode 后句柄失效」，收益与复杂度不成正比，
  暂时保留现在的写法。
- **API 侧的改写仍是整文件重写**（`api/app/message_center.py::_rewrite`）：API 侧
  写入量远低于引擎，且两侧读写的是同一个格式，混用不影响正确性。需要时再改。
- **文件增长以活跃条目为界**：被清理（外部删除行）的条目不会主动回收，压缩只去掉
  被覆盖的版本，不做保留期淘汰。
