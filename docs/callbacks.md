# 回调审计、重放与事件总线

这份文档说明投递回调的可观测部分：每次尝试留下的审计、可重放的事件归档，以及引擎内部的事件总线。回调的事件类型与报文格式见 README 的「投递回调」一节。

## 为什么需要审计

回调是异步的。接收方没收到时的第一个问题永远是「到底发过没有、发了什么、为什么失败」，而日志是流水：按事件标识回查只能 grep，重试的中间态与被丢弃的事件都容易被读成「没发生过」。

引擎因此把两件事落成可查的事实：

| 文件 | 内容 | 配置 |
| --- | --- | --- |
| 审计 | 每次发送尝试一行 JSONL | `XW_CALLBACK_AUDIT_FILE`（默认 `api/data/callback_audit.jsonl`） |
| 归档 | 事件正文，供重放 | `XW_CALLBACK_EVENT_FILE`（默认 `api/data/callback_events.jsonl`） |

两个变量写 `off` / `disabled` / `none` / `-` 即关闭。

## 审计行

一行一次尝试，字段与排查动作一一对应：

| 字段 | 含义 |
| --- | --- |
| `event_id` / `event` | 事件标识与类型，接收方手里通常只有前者 |
| `trigger_id` | 把一次触发的多条事件串起来 |
| `target` | 脱敏后的地址（协议 + 主机 + 路径，不含查询串与凭据） |
| `attempt` | 第几次尝试，从 1 开始 |
| `status` | `delivered` / `retrying` / `failed` |
| `http_status` / `error` | 接收方状态码与失败原因 |
| `retryable` | 这次失败是否还会再试 |
| `duration_ms` / `at` | 耗时与记录时刻 |

三种状态里 `retrying` 单独一档而不是并入 `failed`：一次最终成功的事件中间也会有失败尝试，把中间态记成失败会让「最近失败」列表里混进已经恢复的事件。

队列满或分发器关闭导致的丢弃同样记一行（`attempt=0`，`status=failed`，原因是 `queue_full` / `closed`）。没有这一行，「事件没发出去」在日志里就是一段空白。

## 归档与重放

事件正文**在入队之前**归档，所以被丢弃的事件也能重放。单条正文超过 1 MB 拒绝留存——回调报文本身不大，超过这个量的多半不是本引擎写出来的记录。

```
POST /admin/webhook/replay
{"ids": ["9f2c…", "1a7b…"]}
```

回执分四段：`replayed`（已重新入队）、`missing`（归档里没有）、`filtered`（没订阅该类型，未重放）、`dropped`（入队时队列满）。只给一个总数回答不了「为什么这条没重放」，四段能逐条对上。

两条语义值得注意：

- **保留原事件标识**，并把报文的 `replay` 置为 `true`。接收方据此区分「补发」与「新事件」，不必自己记录哪条处理过。
- **重跑订阅筛选**。没订阅的类型即使存档里有也不会发出去：运维动作不该顺手改变接收方的流量口径。被筛掉的标识出现在 `filtered` 里，而不是静默消失。

单次上限 100 条：重放会立刻产生真实 HTTP 请求，影响面与一次群发相当，逼调用方分批确认。

## 运维接口

监听地址由 `XW_ADMIN_ADDR` 指定（默认 `127.0.0.1:8081`，写 `off` 关闭）。

| 接口 | 用途 |
| --- | --- |
| `GET /admin/health` | 队列、分发器与渠道实现的健康快照 |
| `GET /admin/webhook/events` | 按 `event_id` / `type` / `status` / `since` / `until` 翻页查审计（`limit` 上限 500，时间是 RFC3339） |
| `POST /admin/webhook/replay` | 按事件标识重新投递 |
| `GET /admin/events/recent` | 最近若干条事件（新的在前），确认「刚才那条互动有没有产生事件」 |
| `GET /admin/providers`、`GET /admin/metrics` | 渠道实现健康与投递指标 |
| `GET /admin/dead-letters`、`POST /admin/dead-letters/{replay,discard}` | 死信查询、重放与丢弃 |

参数写错返回 400 并说明是哪个参数——返回一个空列表会让人以为「就是没有记录」。审计能力缺失时（文件打不开只告警）不注册前两条路由，404 比一张空表更诚实。

## 文件滚动

审计与归档都是追加写，不滚动就会随运行时长无限增长：跑到第三个月发现文件几十 GB，那时连按标识回查都变成一次全文件扫描。

超过 8 MB 时裁到「最近 5000 行且总量不超过 4 MB」。两个条件都要满足——只按行裁，行长一变（事件带互动者列表）就可能裁完仍超阈值，于是每次写入都重写一次；只按字节裁，则一行都可能留不下。重写前先关闭追加句柄（旧 inode 上的写入会丢），走「临时文件 + 改名」，崩在中间最多留一个残缺的临时文件，而不是半份审计。

## 事件总线

引擎内部的事件分发走一条进程内总线（`engine/internal/eventbus`）：

- `Publish` 只做非阻塞入队。每个订阅者一条独立有界队列与 goroutine，慢订阅者塞满自己的队列后只丢自己的事件并计入 `dropped`，不会把发布方或别的订阅者拖住。
- 主题支持 `*` 与 `delivery.*` 这类**尾缀通配**，不支持中间通配。订阅表达式越宽松，「以为订阅了却匹配不到」的写法越多，而装配期报错比运行期丢事件便宜。
- 处理器 panic 被 recover 并计失败：一个消费者的 bug 不该让引擎退出。
- `Close(ctx)` 停止收新事件后按宽限排空，与队列、分发器的退出语义一致。

回调分发与「最近事件」环形缓冲都挂在这条总线上，新增一个消费者只需要一次 `Subscribe`。`Stats()` 给出总线级与逐订阅者的收到 / 丢弃 / 处理 / 失败 / 待处理，健康的判断标准是丢弃数长期为 0。
