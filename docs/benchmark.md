# 队列链路压测报告

本文记录 `engine/cmd/xwbench` 在一台开发机上的测量结果，重点回答两个问题：

1. 「入队 → 领取 → 处理 → 确认」这条链路在一台机器上能跑多快，瓶颈在哪一段；
2. 把「一条消息一次脚本往返」改成「一次往返取一批」之后，吞吐与延迟各变化多少。

数字都是本机实测，不含网络跳数与跨机调用，不能当作线上容量承诺；它描述的是
这条链路自身的形态与相对变化，用于判断下一次该优化哪一段。

## 测试环境

| 项目 | 配置 |
| --- | --- |
| 机型 | Apple M4 Pro，12 核 |
| 内存 | 24 GiB |
| 系统 | macOS 26.6（arm64） |
| Go | 1.27.3 darwin/arm64 |
| Redis | 8.10.1，本机回环，`--save '' --appendonly no`（不落盘） |
| 拓扑 | 生产者、消费者、Redis 在同一台机器、同一个进程里（消费者跑在压测进程内） |

生产者、消费者与 Redis 抢同一份 CPU，这是本组数据的最大前提：消费者开得越多，
留给生产者的核越少，写入速率会随之下降（场景 1 的批量列可以看到这个现象）。

## 测量口径

- **吞吐**：`(处理成功 + 处理失败) / 窗口`。窗口是「第一条消息入队 → 最后一条消息确认完成」。
- **端到端延迟**：消息体里带一个入队时间戳，消费者在确认前打点，样本含排队时间。
  批量领取时一批消息共用一个领取时刻，但延迟仍按各自消息体的时间戳算，因此排队时间是真实的。
- **窗口终点**：取最后一次确认的时刻，而不是压测收尾函数返回的时刻。收尾时可能有消费者正阻塞在
  「队列已空」的等待里，等它退出要花掉一个 `pollTimeout`；把这算进窗口会把吞吐压低一截
  （改动前同参数下 8 消费者只测到 9,981 条/秒，改动后 21,526 条/秒，差异全部来自这一段等待）。
- **失败消息仍会确认**：压测只关心链路吞吐，让失败消息按租约反复重投会把统计搅成噪音，
  失败条数单独计进错误率。
- **内存**：取 Go 运行时口径（堆、在用、保留、累计分配、GC 次数），不是进程 RSS。
- 每个场景连跑 3 次，报告取中位数；3 次之间的离散度在 1% 以内（2ms 处理场景约 4%）。

## 场景与结果

### 场景 1：解码路径，消费者数扫描

20,000 条消息，生产者并发 16，不限速，消费者分别取 4 / 8 / 16，只解码不执行管线。

| 消费者 | 每条一次领取+确认 | | 一次领取 32 条 | |
| --- | --- | --- | --- | --- |
| | 吞吐（条/秒） | P50 / P99 | 吞吐（条/秒） | P50 / P99 |
| 4 | 14,897 | 586ms / 1.05s | 58,703 | 0.4ms / 0.9ms |
| 8 | 21,526 | 357ms / 607ms | 53,346 | 0.4ms / 0.8ms |
| 16 | 29,336 | 200ms / 277ms | 45,092 | 0.4ms / 0.8ms |

两个现象值得记下来：

- 单条领取时吞吐随消费者数近似线性增长（14.9k → 21.5k → 29.3k，每翻倍 +46%），
  说明这一段没有并发冲突，缺的是并行度；但延迟随积压线性上涨，因为消费速度追不上写入速度。
- 批量领取后 20,000 条在写入窗口内就被消费完，延迟掉到亚毫秒级，此时报出的吞吐等于**写入速率**：
  消费者越多，生产者分到的 CPU 越少，写入反而慢（58.7k → 53.3k → 45.1k）。
  这一列已经不是消费能力的上限，而是「生产者能写多快」。

### 场景 2：加大总量，观察稳态

100,000 条消息，生产者并发 32，消费者 8。

| 领取方式 | 写入（条/秒） | 吞吐（条/秒） | P50 | P99 | 堆 |
| --- | --- | --- | --- | --- | --- |
| 每条一次 | 92,933 | 21,368 | 2.10s | 3.58s | 6.2 MiB |
| 一次 32 条 | 70,546 | 70,558 | 0.6ms | 1.2ms | 4.6 MiB |

单条领取时写入远快于消费（93k 对 21k），队列一路积压，P50 就是排队时间（2.1 秒）。
批量领取后消费追平写入，队列不积压，吞吐由写入端决定。批量那一行的写入反而更低，
是因为消费者占着 CPU 不放，生产者拿不到与单条领取时同样多的核。

### 场景 3：继续压写入端，试探消费上限

消费者固定 8 个、每次领取 32 条，只加大生产者并发。

| 生产者并发 | 总条数 | 写入（条/秒） | 吞吐（条/秒） | P99 |
| --- | --- | --- | --- | --- |
| 32 | 100,000 | 70,546 | 70,558 | 1.2ms |
| 64 | 100,000 | 88,327 | 88,362 | 2.2ms |
| 96 | 150,000 | 93,718 | 93,765 | 3.2ms |

三组里消费侧都跟得上写入，P99 始终在毫秒级。**本轮没有测出消费端的上限**：写入端先饱和了
（每条消息一次 `LPUSH`，Redis 单线程执行），要继续往上压，得先把写入端改成批量。

### 场景 4：完整执行管线（聚合 + 站内信 + 推送）

20,000 条，生产者并发 16，消费者 8，消费者执行真实管线：同帖点赞聚合成一张卡片、写站内信、
走推送 provider（收件箱用内存实现，避免磁盘写主导测量）。

| 领取方式 | 吞吐（条/秒） | P50 | P90 | P99 | 堆 |
| --- | --- | --- | --- | --- | --- |
| 每条一次 | 18,490 | 451ms | 677ms | 729ms | 20.5 MiB |
| 一次 32 条 | 50,564 | 1.2ms | 21.7ms | 24.7–31ms | 16.5 MiB |

管线路径的 P99 明显高于纯解码（1.2ms → 25ms）：聚合卡片的读改写与站内信写入是串行段，
一批消息里只要有一条撞上这段落，整批的确认就往后推。这是有意的取舍——
先把「不积压」做到，再谈单条延迟。

### 场景 5：每条消息带 2ms 处理耗时

8,000 条，生产者并发 16，消费者 8，每条模拟 2ms 处理。理论上限 8 / 2ms = 4,000 条/秒。

| 领取方式 | 吞吐（条/秒） | P99 |
| --- | --- | --- |
| 每条一次 | 2,679 | 2.85s |
| 一次 32 条 | 3,288 | 2.23s |

这一组是「优化不改变结论」的对照：处理耗时本身占大头时，减少往返只带来 23% 提升
（2,679 → 3,288），离理论上限仍有距离，差额来自批内串行处理——一批 32 条要一条条跑完才确认。
真正要提高这一段，得让同一批里的消息并行执行，而不是继续加大批量。

## 瓶颈定位

按场景 1–3 的数据，单条领取时的瓶颈是**每条消息两次 Lua 脚本往返**（领取一次、确认一次）：

- 领取脚本要做 `LPOP`/`RPOP` + `HSET` + `ZADD`，确认脚本要做 `HDEL` + `ZREM`，
  Redis 单线程逐条执行脚本，消费者开得再多也只是把请求排在同一个执行队列里；
- 证据是吞吐随消费者数近似线性增长、但每条消息的耗时不变（8 消费者下 21,526 条/秒 ÷ 8 ≈ 2,690 条/秒/消费者，
  即一条约 0.37ms），说明不是 CPU 打满，而是往返在排队；
- 反过来，延迟的绝对值随积压线性上涨（P50 从 200ms 到 2.1s），也是排队而非计算的表现。

## 优化：批量领取与批量确认

改动落在队列层，不改变可靠性语义：

- `queue.ReliableConsumer.ClaimBatch(ctx, max)`：一条 Lua 脚本内循环取出至多 `max` 条，
  逐条写 `HSET`/`ZADD` 登记在途记录，领取凭据为「纳秒+随机前缀-序号」，并发消费者不会撞号；
- `queue.ReliableConsumer.AckBatch(ctx, ids)`：一条脚本内逐条 `HDEL` + `ZREM`，重复确认仍是空操作；
- `worker.BatchConsumer` 接口 + `Worker.WithPrefetch(n)`：预取大于 1 且消息源支持批量时走批量路径，
  队列空时退回单条领取借它的阻塞等待，避免空转；一批消息处理完统一确认；
- 配置项 `XW_PREFETCH`（默认 1，即逐条；上限 512）。

批量大小的取舍：一批消息在领取后到确认前都占着在途记录，批量越大、单条消息离租约到期越近。
按默认 60 秒租约，512 条约有 100ms 级的余量，够一次渠道调用；默认值保持 1，
需要吞吐时再显式开启，避免在慢渠道上把租约余量吃掉。

优化前后（同机器、同参数、各 3 次取中位数）：

| 场景 | 优化前 | 优化后 | 变化 |
| --- | --- | --- | --- |
| 解码 20k / 8 消费者 | 21,526 条/秒，P99 607ms | 53,346 条/秒，P99 0.8ms | 吞吐 ×2.5 |
| 解码 100k / 8 消费者 | 21,368 条/秒，P99 3.58s | 70,558 条/秒，P99 1.2ms | 吞吐 ×3.3 |
| 完整管线 20k / 8 消费者 | 18,490 条/秒，P99 729ms | 50,564 条/秒，P99 25ms | 吞吐 ×2.7 |
| 2ms/条 8k / 8 消费者 | 2,679 条/秒，P99 2.85s | 3,288 条/秒，P99 2.23s | 吞吐 ×1.2 |

结论：往返次数是这一段的成本主导项时（无处理耗时、或处理很轻），批量领取把吞吐抬到 2.5–3.3 倍，
延迟从「排队秒级」降到毫秒级；处理耗时本身占主导时收益有限，瓶颈换成了批内串行执行。

## 尚未解决

- **写入端成为新上限**：批量领取后消费能跟上 94k/秒的写入，但每条消息仍是一次 `LPUSH`。
  写入要再快，得在生产者侧做批量入队（`RPUSH` 多值），这会改变「一条消息一次入队结果」的
  错误语义，暂未实施。
- **批内串行**：一批消息在同一个消费者里顺序执行，慢步骤会把整批的确认推后。可考虑批内并发，
  但需要重新考虑「一批里失败几条」时的确认边界。
- **管线路径的 P99 由聚合与站内信写入决定**，与队列改造无关，属于下一步要单独看的段落。
- **未测出消费上限**：写入端先饱和，消费端的拐点还没有数据。
- 所有数据都来自单机同进程，Redis 无持久化；跨机、开 AOF、或在容器里限核，数字都会明显不同。

## 附录：邮件投递的连接复用

上面的场景测的是队列链路；这一段单独看渠道侧的固定开销。一条 SMTP 连接在可用
之前要走完 TCP、STARTTLS 握手、EHLO、AUTH 四步，这些步骤与消息内容无关，却是
按条付钱的。把连接留下来复用，省掉的正是这一整段。

| 场景 | 每封耗时 | 单协程吞吐 |
| --- | --- | --- |
| 明文，连接复用 | 92–96 µs | ≈ 10.6k 封/秒 |
| 明文，每封新建连接 | 195–200 µs | ≈ 5.1k 封/秒 |
| STARTTLS + AUTH，连接复用 | 93–97 µs | ≈ 10.6k 封/秒 |
| STARTTLS + AUTH，每封新建连接 | 478–485 µs | ≈ 2.1k 封/秒 |

- 复用后每封仍有五个往返（NOOP 存活确认、MAIL、RCPT、DATA、结束符），因此明文与
  加密链路的单封耗时几乎一样：握手与认证已经摊到第一条消息上了。
- 不复用时加密链路每封都要重新握手并重新认证，成本涨到 5 倍。真实中继上还要加上
  网络 RTT，差距会更大——这份数据在回环上测，RTT 近似为零。
- 毫秒级的中继延迟会把两条曲线都抬高，但差值是固定的那一部分，复用省的正是它。

## 复现

```bash
# 独立端口的 Redis，不影响已有实例
redis-server --port 6399 --save '' --appendonly no --daemonize yes

cd engine
go build -o bin/xwbench ./cmd/xwbench

# 解码路径，逐条领取
./bin/xwbench -redis 127.0.0.1:6399 -total 100000 -concurrency 32 -workers 8 -flush
# 解码路径，每次领取 32 条
./bin/xwbench -redis 127.0.0.1:6399 -total 100000 -concurrency 32 -workers 8 -prefetch 32 -flush
# 完整管线
./bin/xwbench -redis 127.0.0.1:6399 -total 20000 -concurrency 16 -workers 8 -prefetch 32 -pipeline -flush
# 加 2ms 处理耗时
./bin/xwbench -redis 127.0.0.1:6399 -total 8000 -concurrency 16 -workers 8 -prefetch 32 -work 2ms -flush
```

`-flush` 只清 `xw:queue:bench` 及其衍生键（在途、重试、死信），不动触发链路的队列。
`-json` 输出留档形态，便于把多组结果放在一起比较。
