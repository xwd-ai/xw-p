# 请求限流

`/v1` 下的接口共用一层令牌桶限流，按「凭据」或「来源 IP」判定。默认关闭，
配置了额度才生效。

## 配置

| 变量 | 默认 | 说明 |
| --- | --- | --- |
| `XW_RATE_LIMIT_KEY_RPM` | `0` | 每个凭据每分钟的请求数，`0` 表示该维度关闭 |
| `XW_RATE_LIMIT_IP_RPM` | `0` | 每个来源地址每分钟的请求数，`0` 表示该维度关闭 |
| `XW_RATE_LIMIT_BURST` | `0` | 允许的突发深度，`0` 表示取该维度的每分钟额度 |
| `XW_RATE_LIMIT_BACKEND` | `auto` | `auto` 跟随 `XW_BUS`（Redis 总线用 Redis），也可显式 `redis` / `memory` |
| `XW_RATE_LIMIT_PREFIX` | `xw:ratelimit` | Redis 键前缀 |
| `XW_RATE_LIMIT_TIMEOUT` | `0.5` | 单次取令牌的等待上限（秒） |
| `XW_RATE_LIMIT_TRUST_FORWARDED` | 关 | 是否采信 `X-Forwarded-For` |

```bash
XW_RATE_LIMIT_KEY_RPM=600 XW_RATE_LIMIT_IP_RPM=120 XW_RATE_LIMIT_BURST=60 \
  api/.venv/bin/python -m uvicorn app.main:app --port 8399
```

启动日志会打印实际生效的维度、额度与后端；关闭时也会说明「未启用」以及怎么开，
因为「被拦住了」和「根本没配」在现象上很像。

## 为什么是令牌桶

固定窗口在窗口交界处会放过两倍额度（第 59 秒打满、第 61 秒再打满）。通知接口
的流量本来就是一问一答的短请求，用「容量 + 恒定补充速率」描述更贴切：允许一条
热帖带来的短时突发，长期速率仍被压住，也不需要对齐任何时间边界。

`rpm` 决定长期速率（`rpm / 60` 个令牌每秒），`burst` 决定一次能用掉多少。默认
`burst = rpm`，语义是「一分钟的量可以一次用完」——比给一个与速率无关的常量好解释。

## 凭据优先，IP 兜底

一次请求只消耗一个桶：

- 请求带 `X-Api-Key` 且命中 `XW_API_KEYS` 里声明的 Key，或带验签通过的 Bearer
  令牌 → 按凭据计。键里放凭据摘要，不落原值：限流键会出现在 Redis 和各处排查日志里，
  长期 Key 是能发通知的凭证。令牌按「租户 + 主体」聚合，重新登录换了令牌不会重置额度。
- 否则按来源 IP 计。

**没配 Key 的部署不会因为调用方填了 `X-Api-Key` 就单独给一个桶**——那样的「凭据」
是调用方自己编的，换个值就换一个桶，等于关掉限流。因此按凭据限流的前提是先配置 Key。

两个维度同时配置时不叠加判定：凭据维度收住可控来源，匿名来源落到 IP 维度，为同一件
事付两次 Redis 往返没有必要。额度上建议让凭据维度显著宽于 IP 维度。

只配凭据维度时，拿不出有效凭据的请求不消耗任何额度（它们会在鉴权那一步收到 401），
所以想拦住「伪造凭据扫描」这类流量，IP 维度也要配上——两个维度是互补而不是互为备份。

## 响应

正常响应带 `X-RateLimit-Limit`（每分钟额度）、`X-RateLimit-Remaining`（还剩几次）、
`X-RateLimit-Dimension`（`key` / `ip`）。超限时返回 429，形状与其它错误一致：

```json
{"detail": "请求过于频繁：来源 203.0.113.7 每分钟最多 120 次，请在 1 秒后重试"}
```

并带 `Retry-After`（整数秒，至少 1）。429 同样经过 CORS 中间件（限流注册在它内层），
浏览器读得到原因，而不会显示成 `Failed to fetch`。

## 后端

`memory` 后端是有序列表 + 惰性补桶，条目数超过上限（默认 1 万）按最久未用淘汰；
它只适用于单进程 demo，多实例部署等于每个实例各有一份额度。

`redis` 后端用一个 Lua 脚本完成「取时间 → 补桶 → 扣令牌 → 写回」：

- 整段脚本在 Redis 里串行执行，多实例共享同一个桶，不会出现「都读到 5 个令牌、
  各自扣一个」的超发；
- 时间取 `redis.call('TIME')` 而不是调用方传参，实例间几十毫秒的时钟偏差不会让补桶量
  随实例漂移；
- 键带 `PEXPIRE`，时长是「从空桶补满 + 一分钟余量」。补满之后的状态与没有这条记录
  等价，留着只是占内存。

## 故障时放行

后端不可用（Redis 连不上、脚本报错、超时）时**放行**并在响应头标
`X-RateLimit-Degraded: true`，告警按 30 秒窗口合并。限流是为了保住服务，它自己坏掉
不该把通知接口变成 503；反过来，如果这里选择拒绝，一个 Redis 抖动就会放大成整站不可用。
调用方看到这个头就知道「没被限」不等于「额度够」。

## 豁免

`/health` 与文档端点（`/docs`、`/redoc`、`/openapi.json`）不在 `/v1` 下，不受限——
负载均衡器的健康探测被自己配的限流挡住，表现是「服务正常但一直被摘掉」。CORS 预检
（`OPTIONS`）也不计入额度：浏览器对每个跨源写请求都会先发一次，算进去等于让 CORS
吃掉一半额度。

`X-Forwarded-For` 默认不信：任何调用方都能自己填，采信它等于「换个头就换一个桶」。
只有部署在会**追加**该头的反向代理之后才打开 `XW_RATE_LIMIT_TRUST_FORWARDED`，
并且取最右一段——那是最近一跳代理写下的真实地址，左边的部分仍可能是伪造的。
