# 多租户与环境隔离

租户是比环境更高一层的数据边界：环境区分同一套业务数据的 dev / prod 副本，租户区分互不可见的客户，两者正交——一个租户有自己的 dev 与 prod。

## 请求头

| 头 | 取值 | 缺省 |
| --- | --- | --- |
| `X-Tenant-Id` | 小写字母、数字、连字符、下划线，≤32 位 | `default` |
| `X-Environment` | `development` / `production` | 服务端 `XW_ENV` |
| `X-Api-Key` | 配置了 Key 时必填 | — |

租户标识的字符集收得很紧，因为它会拼进数据文件路径：放开 `..` 与 `/` 就能跳出数据目录。写错或不在 `XW_TENANTS` 清单内直接 400，而不是悄悄退回默认租户——静默落到别人的数据里比报错难查得多。

`XW_TENANTS` 用逗号分隔声明这套部署存在哪些租户。清单里没有 `default` 时（只服务少数客户是常见部署），不带租户头会返回 400 并列出可用租户：这时缺的是头，不是标识写错，报「未知租户：default」只会让人去改一个没错的值。

## 状态码口径

| 状态码 | 场景 |
| --- | --- |
| 400 | 环境头非法、租户标识非法或不在清单内、缺少租户头且清单里没有 `default` |
| 401 | 没带 Key、Key 不认识、Key 不覆盖当前环境 |
| 403 | Key 命中，但请求头指明了另一个租户 |

环境不匹配也用 401 而不是 403：403 会让调用方区分出「这个 Key 是真的、只是用错了环境」，等于给出凭证探测的信号。用错环境本来就是这个 Key 在当前请求里不成立。403 只用于越权——拿自己的凭据访问别人的数据。

## API Key 作用域

`XW_API_KEYS` 是 JSON 数组，每个元素声明一个 Key 绑定的租户与允许的环境：

```json
[
  {"key": "sk_live_acme", "tenant": "acme", "environments": ["production"], "label": "社区主站"},
  {"key": "sk_test_acme", "tenant": "acme", "environments": ["development"]}
]
```

- `environments` 省略表示不限环境；也接受 `"development, production"` 这种逗号分隔写法。
- 配置写错（非 JSON、缺 `key`、租户标识非法、未知环境）在加载时抛错，不静默跳过：跳过一条的表现是「配了 Key 却一直 401」，比起动失败难查。
- 没配置任何 Key 时保持 demo 语义：租户由请求头决定，本地直接可用。

旧的按环境 Key（`XW_API_KEY_DEVELOPMENT` / `XW_API_KEY_PRODUCTION`）升级后行为不变：它们被折算成「绑定默认租户、只允许自己那个环境」的作用域，与显式声明的 Key 合并成同一张表；同一个 Key 出现在两个环境时合并成一条。

## 数据分区

默认租户沿用原有路径，升级不必搬迁数据；其余租户落在同级的 `tenants/<租户>/` 目录下，文件名不变。

| 数据 | 默认租户 | 其他租户 |
| --- | --- | --- |
| 订阅者 / 分组 / 偏好 / 已读状态 | `api/data/subscribers.jsonl` 等 | `api/data/tenants/<租户>/subscribers.jsonl` 等 |
| 工作流、活动日志、执行明细 | 记录带 `tenant` 列/字段并按它过滤；Postgres 用 `COALESCE(tenant,'default')` 兼容老行 | 同左 |
| 幂等键 | 进程内一张表 | 键加租户前缀（同键不同租户不会互相顶掉） |
| 收件箱 | 多个租户共用的追加文件，条目带 `tenant` / `environment`，读取时按两者过滤 | 同左 |

收件箱的缓存键包含租户与环境：同一个订阅者标识可能出现在多个租户里，只用标识做键会让一个租户读到别人的快照。

引擎侧同样带着这两个维度：队列消息、投递请求、收件箱条目、聚合卡片与执行明细都有 `tenant` / `environment`，空值折算成默认值（升级前入队的消息没有这两个字段，写空值会撑破默认租户的视图）。

## 环境隔离

环境之间的边界落在「记录的键」上，而不只是记录里多一个字段。

| 资源 | 键 | 跨环境访问 |
| --- | --- | --- |
| 订阅者 | `(环境, 标识)` | 读、改、删一律 404；两套环境可以有同一个标识与同一个邮箱 |
| 工作流 | `(环境, 名称)` | 按标识读、改、启停、复制、删除一律 404；同名模板在两边各有一份 |
| 偏好 / 分组 / 收件箱 / 活动 / 执行明细 | 带环境字段 | 读取时按环境过滤，分组广播逐成员校验环境 |

同一标识在两套环境各有一条档案是刻意的：本地给某个人加一个测试邮箱、改一次渠道绑定，不该动到线上那个人。地址唯一性也按环境判定——同一邮箱在开发与生产各绑一次是正常的，在同一环境里绑两个人仍然 409。

按标识访问另一套环境的记录返回 404 而不是 403：403 等于告诉调用方「这个标识确实存在，只是不在你这边」，而它和「本环境没有这个标识」对调用方是同一件事，不需要区分。

**写操作只落在请求头指明的环境**。创建或更新时请求体里的 `environment` 要么不传（跟随 `X-Environment`），要么与之一致，写错返回 422；复制工作流同理，不能把副本顺手写到另一套环境。理由与 Key 作用域是同一个：允许一个请求写另一套环境，存储层做得再细也会从这个入口漏掉。跨环境搬运数据请带目标环境的头单独调用。

按名称查找模板必须带环境（`get_by_name(name, environment=...)`）：两套环境有同名模板时，不带环境的查找会拿到先写入的那份，表现为「生产的触发跑了本地的模板」——改名之后才会暴露，属于最难查的一类故障。

管理端接口（`/v1/admin/*`）刻意可以跨环境：排障时通常要同时看两套环境，那里的 `environment` 是显式查询参数，默认不按请求头收窄。

已知限制：`scripts/migrations/002_core_entities.sql` 还是按租户之前的结构（`workflows.name` 全局唯一、没有 `tenant` 列），内存与 JSONL 后端按本节实现；Postgres 建表脚本与上述约束对齐属于后续工作。

## 隔离范围

租户覆盖的是业务数据：触发、订阅者、偏好、分组、工作流、活动与执行明细、收件箱。

渠道配置与投递汇总（`GET /v1/providers`、`GET /v1/dashboard/stats`）仍是部署级——一套部署一套 SMTP/SMS 凭据，把它们做进租户意味着每个租户都要单独配通道，那是另一件事。`GET /health` 也不区分租户。

## 运营后台

后台不单独做租户切换：地址栏带 `?tenant=acme` 进一次，后续页面沿用同一个租户（记在 `localStorage`）。切租户等于换一套数据，重新进一个链接比在页面里留一个能改全局状态的控件更不容易出错。
