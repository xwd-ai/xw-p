# 幂等键：语义、并发裁决与验证

触发接口（`POST /v1/events/trigger`、`POST /v1/events/trigger/batch`、`POST /v1/topics/{id}/trigger`）
都接受 `Idempotency-Key` 请求头。同一条互动在客户端重试、网关重发、部署滚动时被提交
两次是常态，服务端必须能回答「这次和上次是不是同一件事」。

## 语义

| 情况 | 结果 |
| --- | --- |
| 不带 `Idempotency-Key` | 每次请求都是一次新的触发，生成新的触发标识 |
| 键首次出现 | 入队，回执里的 `triggerId` / `transactionId` / `acknowledgmentId` 本次生成 |
| 键出现过且回执可读 | 不入队，原样返回首次那份回执（包括「首次就被拒的条目」） |
| 键存在但回执读不出来 | `409`，**且没有入队** |

最后一行是这个模块最容易被写成 bug 的地方。去重的实现是「原子写入失败 → 回读回执」，
回读为空意味着键在存储里、内容却读不到（值被写坏、或刚好撞上 TTL 边界）。此时若按
「未命中」继续入队，同一个键就会产出第二条通知，而这正是幂等要防的事。所以这里选择
明确失败：调用方拿到 `409`，知道本次没有入队，可以按触发标识去活动日志确认前一次
是否已受理。三个入口共用同一条判定（`api/app/idempotency.py` 的 `claim()`），不各写一遍。

键的作用域是「请求体里的这一次/这一批/这一轮广播」，不是「这些事件」：批量与广播
缓存的是整次请求的回执，重放时连「哪些条目当时被拒、原因是什么」都一致。

## 处理顺序与代价

三条入口的顺序一致：

1. 解析工作流（不存在或未启用 → 404，不占用键）；
2. 构造消息与回执；
3. 占用键（`claim`）；
4. 写活动日志，再把消息交给总线。

**先占键、后入队**是为了让「并发同键」只有一个赢家：抢占失败的请求在入队之前就返回了
首次回执。代价是一段很短的 at-most-once 窗口——占键之后、入队之前进程被杀，键已经
被占而消息没进队列，之后同键的重试只会拿到那份回执，不会补发。要彻底消除这个窗口
需要把「写幂等记录」与「入队」放进同一个事务（例如在 Redis 里用 Lua 把 `SET NX` 与
`LPUSH` 合成一步），代价是耦合队列实现与幂等实现；当前的取舍是保持两者可独立替换，
并把这个窗口写在这里而不是留给使用者猜。

分组广播还有一个次要点：先把整组展开（逐成员解析档案、构造消息），再占键。并发同键
的两次广播会各展开一遍，只有一份入队。展开是纯计算、不产生副作用，重复一遍的代价
可以接受；把占键提前则需要「先写占位回执、算完再覆盖」，多一次写入与一个中间态。

## 后端选择

| 后端 | 适用 | 原子性来源 |
| --- | --- | --- |
| `memory`（默认） | 单进程 demo、测试 | 进程内锁 |
| `redis` | 多实例部署 | `SET key value NX EX ttl` |

`XW_IDEMPOTENCY=redis` 配套 `XW_REDIS_URL`；键前缀 `xw:idem:`，非默认租户再加
`<租户>:` 前缀——幂等键由调用方生成（常见写法是业务单号），两个租户用同一个键完全
正常，不加前缀会让后到的租户命中前一个租户的回执。TTL 由 `XW_IDEMPOTENCY_TTL`
控制（默认 86400 秒），窗口内重放返回回执，过期后同一个键会被当成新请求。

`memory` 后端在多实例下**不成立**：每个进程一份字典，同一键在两个实例上各入队一次。
这类部署必须切到 `redis`，否则「幂等」只在单个进程内有效。

## 验证

### 多实例并发（真实链路）

```bash
# 自己起 2 个实例 + 一个临时 redis-server，同键 200 并发
python scripts/idem_stress.py --instances 2 --requests 200 --concurrency 32

# 打已有部署；不给 --redis 时跳过队列核对，只按回执判定
python scripts/idem_stress.py --base-url http://127.0.0.1:8000 --redis redis://127.0.0.1:6379/0
```

脚本跑两轮：**同键轮**（N 个请求携带同一个键，均匀分散到各实例）与**异键轮**
（N 个请求各带一个键）。判定依据是队列里实际多出几条消息，而不是只看回执——回执是
服务端自己写的，`LLEN` 才是投递链路真正会发生的事。异键轮用来反向确认去重没有过头。

本机实测（2 个实例，环回地址，内存 32 并发）：

```
同键并发：200 个请求 / 0.138s
  响应：200×200
  触发标识：1 个
  入队：1 条
异键并发：200 个请求 / 0.209s
  响应：200×200
  触发标识：200 个
  入队：200 条
结论：通过
```

这是正确性核对，不是吞吐基准：环回、无 TLS、单条小报文，数字只说明「没有多发」。
吞吐与延迟口径见 [`benchmark.md`](benchmark.md)。

### 回归用例

`api/tests/test_idempotency_concurrency.py` 按「离线上限 → 真链路」三层：

- 进程内 32 线程打同一接口：只产出 1 个触发标识、1 条消息、1 条活动日志；异键 24 并发
  全部入队；整批同键 16 并发只入队 2 条（2 条是批内消息数）。
- 4 个独立进程各持一个 Redis 客户端同一时刻抢同一个键：恰好 1 个 `claimed`、3 个
  `replay`。这一层证明裁决点是 `SET NX`，而不是某个进程内的锁。
- 两个 uvicorn 实例共享同一份 Redis：60 个同键请求只入队 1 条，异键轮 60 条各入一条，
  活动日志正好 61 行。

反向验证过用例确实有效：把内存后端的 `put_if_absent` 换成非原子的「先查后写」，
进程内那组立刻出现多条入队。

## 已知边界

- 占键成功但入队前进程退出：键已占、消息未入队，同键重试不会补发（见上文 at-most-once 窗口）。
- 回执不可读时返回 `409`：同键重试会持续得到 `409` 直到 TTL 过期，此时应换新键，
  或先按触发标识确认前一次是否已受理。
- `memory` 后端不跨实例，多实例部署必须用 `redis`。
- 压测与集成测试用 `XW_ACTIVITY_FILE` 把活动日志写进临时目录，避免污染本地 demo 数据；
  该变量只影响 `jsonl` 后端的落盘位置。
